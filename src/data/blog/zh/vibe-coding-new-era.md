## 它不是“让 AI 替你写代码”

最常见的误解：vibe coding = 不知道自己在干什么。事实恰恰相反。要让 AI 产出有用的代码，你需要：

- **清楚自己到底要什么**——提示词的精确度，与开发者的经验成正比。
- **能评估输出**——分辨地道的代码和“跑得起来但是颗定时炸弹”的代码。
- **能引导迭代**——知道什么时候该转向，什么时候该否决，什么时候该接受。

Vibe coding 是用高速执行的高层设计。它不取代技术判断，而是**放大**技术判断。

## 实践中的流程

今天一次典型的 vibe coding 循环是这样的：

1. **意图清晰**——准确定义_做什么_和_为什么_。
2. **AI 快速起草**——拿到 70-80% 可用的功能代码。
3. **审查与引导**——纠正方向，澄清不变式，补充上下文。
4. **迭代打磨**——几轮短平快的循环，直到结果站得住。
5. **测试与最终审查**——这一步永远不能省；你不盯着，AI 就会引入技术债。

---

> 最有价值的不是原始速度，而是 AI 把你从*认知滚动*里解放出来——那层隔在你和真正问题之间的样板代码和语法。

## 更值钱的技能

Vibe coding 并没有让所有技术技能作废，只是重新分配了它们的价值：

**更值钱的：**

- 架构与系统设计
- 判断哪些代码长期可维护
- 写出精确、带上下文的提示词
- 代码审查与问题模式识别
- 领域规则的知识（业务、安全、UX）

**相对贬值的：**

- 背语法
- 手写样板代码
- 把每个库的 API 都记在脑子里

## 这是文化上的变化，不只是技术上的

一些开发者抗拒 vibe coding，理由很情绪化，也很正当：控制感。亲手写下每一行，会让人觉得完全理解了系统。但在大型项目里，那种感觉本来就有一部分是幻觉。

问题不是*我该不该用 AI*，而是*我该怎么信任一个并非完全由自己写的系统*。答案和从前一样：**测试、评审、判断力**。只不过现在要应用到更大的产出量上。

未来的开发者，不是写得最多的人，也不是最少用 AI 的人，而是能用最好的判断力、拿起最好的工具，做出**能跑起来的系统**的人。
